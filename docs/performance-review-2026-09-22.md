# CGRX: анализ графа и производительности, 22 сентября 2026

## Область анализа и достоверность

Анализ относится к CGRX, включая runtime, поиск похожего кода и React-визуализатор.
База изменений — `b29ed13336124d5948403c56f268a2eb046da5a7`.
CGRX MCP: поколение графа `7382526655094679`, 3245 узлов и 9914 рёбер.
Для поиска использованы `status`, `search_graph`, `trace_path`, `orient`,
`check_index_coverage`, `get_architecture` и `scan_risks`; выводы проверены исходниками.

Покрытие частичное: основные Rust/TSX-файлы имеют пропуски разрешения вызовов,
а `dense-layout.js` исключён из структурного индекса. Его поведение проверено
чтением исходников, тестами и замерами. Счётчики пропусков различаются по области
запроса и не являются числом подтверждённых дефектов.

Архитектурная проекция `crates/**`, глубина пакетов 2: 9 пакетов, 12 границ,
2 сообщества пакетов. Циклов среди доступных доказанных связей не обнаружено;
это не доказательство отсутствия циклов во всём исходном коде.

## Что следует из структуры

Основные производственные узлы с высокой входящей связностью:

| Узел | Входящие связи в проекции | Вывод |
|---|---:|---|
| `Hash32` | 83 | Общий тип идентичности; большое число использований ожидаемо |
| `pack_for_path` | 75 | Общий выбор языкового анализатора; сохраняем единый контракт |
| `optional_flag` | 30 | Разбор CLI; число вызовов не доказывает дороговизну |
| `update` в language pack | 29 | Общий механизм извлечения; требует точного контекста вызова |
| `from_value` в MCP | 27 | Граница протокола; важнее корректность схем, чем уменьшение fan-in |

Тестовый `git` имеет 112 входящих связей. Его нельзя интерпретировать как
производственный архитектурный дефект. По одной только связности код не дробился.

Подтверждённые пути влияния:

- `index_source` и `normalize_stored` вызывают `refresh_proof_gaps`; изменения
  здесь влияют на индексирование, открытие индекса и актуализацию рабочего дерева.
- `rebuild_similarity_index` и фоновый `schedule` вызывают
  `build_similarity_index_from_input`; оптимизация затрагивает как запуск,
  так и перерасчёт похожего кода после изменений.
- `score_pair` использует `jaccard` для актуальных доказанных вызовов.
  Изменение оценки нельзя проверять только по внешнему виду графа.
- Раскладка вызывалась непосредственно при React-рендере 2D и 3D; это обнаружено
  по исходникам, а не доказано неполным графом JavaScript.

## Реализованные изменения

### Пропуски анализа: квадратичная проверка заменена проходом

Раньше каждый неразрешённый динамический участок проверялся на вложенность во все
остальные: O(D²). Теперь участки сортируются по пути, началу и убывающему концу;
максимальный конец уже встреченного участка позволяет определить вложенность за
один проход. Итого O(D log D), затем O(D).

Сохранены границы файлов, равные границы, пересекающиеся и пустые диапазоны.
Наличие доказательства по-прежнему проверяется по виду отношения и текущему хешу
исходника. Эквивалентность проверена относительно прежнего попарного алгоритма,
а не только относительно примеров нового алгоритма.

### Похожие функции: меньше сравнений строк

Наборы токенов и шинглов фонового индекса один раз получают точные числовые ID.
Кандидатные пары сравнивают упорядоченные числовые массивы вместо строковых деревьев.
Это интернирование с точным равенством строк, без хеш-коллизий и приблизительных
оценок. Список кандидатов, лимиты, веса и округление оценок сохранены.

Размер объединения Jaccard вычисляется через размеры наборов и их пересечение;
отдельный второй обход объединения удалён. Живые доказанные вызовы по-прежнему
добавляются на этапе `score_pair`. Проверены равенство оценок и существующие
сценарии поиска похожего кода и рефакторингов.

### Браузер: раскладка вне основного потока

Существующий D3 используется в отдельном module worker. Это соответствует
[рекомендации D3 для больших статических графов](https://d3js.org/d3-force/simulation).
Новых библиотек нет; worker упакован локально и обслуживается тем же сервером.

- Устаревший расчёт отменяется завершением worker, его результат не попадает в кэш.
- Завершённые раскладки кешируются по объекту неизменяемого графа и размеру области;
  слабые ключи освобождают данные вместе с графом, максимум 4 размера на граф.
- 2D и 3D показывают состояние расчёта; ошибки не запускают блокирующий fallback.
- Тест реально запускает собранный worker и сравнивает все координаты с прежним
  синхронным алгоритмом. Во время расчёта основной цикл событий продолжает работать.
- Опрос неизменившегося снимка больше не создаёт новый React state для всего графа.
- Узлы сообществ группируются за один проход вместо повторного полного фильтра;
  при фокусе подписи сортируются только для нужных узлов.

## Измерения

Release-сборки на одном компьютере; три чередующихся запуска каждой версии.
Данные — неизменённый `cgrx-opensource`: 3216 отображаемых символов, 2250 связей.
Это холодный процесс с существующим локальным индексом, **не** создание индекса
с нуля и **не** холодный дисковый кэш. Детали снимков и все образцы сохранены в
[JSON измерений сервера](benchmarks/2026-09-22-visualizer.json).

| Операция | До, медиана | После, медиана | Изменение |
|---|---:|---:|---:|
| Открытие runtime и запуск HTTP | 1072 мс | 417 мс | −61% |
| Первый `/api/status`, включая актуализацию | 637 мс | 431 мс | −32% |
| Первый ответ графа | 37,4 мс | 36,6 мс | Практически без изменения |
| Повторный ответ графа | 33,4 мс | 32,5 мс | Практически без изменения |

Все шесть ответов графа побайтно идентичны (SHA-256). Сокращение времени не достигнуто
удалением связей, уменьшением лимитов или сокрытием пропусков.

[Измерение раскладки](benchmarks/2026-09-22-layout.json): синхронный расчёт —
878 мс, полный расчёт в worker — 866 мс, синхронная отправка задания — 5,7 мс,
повторное получение из кэша — 0,016 мс. За время worker основной цикл обработал
157 тиков контрольного таймера. Это улучшение отзывчивости, а не обещание ускорения
всего рендера в 150 раз: создание SVG и отрисовка браузером измерением не покрыты.
Замеры под параллельной компиляцией были исключены; значения зависят от нагрузки.

В браузере дополнительно проверен открытый `gd-main`: 5000 видимых узлов и 5521
связь, рабочий фильтр проектов, отсутствие ошибок консоли. Ограничение вида явно
указывает, что полный индекс больше видимой части.

Воспроизведение:

```sh
python3 scripts/benchmark_visualizer.py --binary target/release/cgrx \
  --repo /absolute/path/to/repository --repeats 3 --output /tmp/visualizer.json
node scripts/benchmark_graph_layout.mjs /path/to/repository-graph-response.json
```

## Проверка корректности

- 495 Rust-тестов пройдено, 3 существующих теста проигнорированы штатными атрибутами.
  Включены языковые сценарии, доказательства, похожий код, рефакторинги, актуализация
  индекса, HTTP и переключение проектов.
- 31 JavaScript-тест пройден, включая настоящий bundled worker, отмену,
  обработку ошибок, кэш, координаты, идентичность u64 и неизменность доказательств.
- TypeScript, сборка web, проверка CSP и release-сборка проходят.
- `scan_risks` не выдал новых кандидатов дефектов; указал 6 затронутых вызовов.
  Проверка частичная, с 25 пропусками покрытия, и не заменяет тесты.

## Оставшиеся ограничения и приоритеты

1. **Очередь HTTP и холодная индексация.** Сервер обслуживает запросы последовательно.
   Долгое открытие одного проекта может задержать запросы остальных. Следующий
   архитектурный шаг — ограниченная очередь фоновых задач индексации с отдельным
   состоянием каждого проекта; нужны замеры холодного создания больших индексов
   и тесты отмены/изоляции. Текущая работа ускоряет операции, но не вводит параллельный HTTP.
2. **Большой SVG.** Сам solver теперь фоновый, однако создание тысяч SVG-элементов,
   выделение и панорамирование остаются в основном потоке. Для дальнейшего роста
   приоритет — измерить эти взаимодействия и сравнить Canvas/WebGL с доступным
   SVG-представлением. Лимит 5000 узлов / 30000 связей сохранён.
3. **Частые изменения кода.** Фоновый similarity worker отклоняет устаревший результат
   по epoch, но уже запущенная работа не прерывается внутри расчёта. Нужен отдельный
   стресс-тест серии сохранений, прежде чем менять управление этими потоками.
4. **Покрытие доказательств.** Отсутствующие рёбра и исключённый JS не подтверждают
   отсутствие зависимостей. Улучшение извлечения — отдельная задача качества,
   которую следует оценивать precision/recall на фиксированных наборах, а не
   ростом количества рёбер на картинке.
